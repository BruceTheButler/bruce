# AI Workflow Guide

## Generated project

`Bruce.xcodeproj` is generated by XcodeGen and gitignored.

```sh
just generate
just open
```

Edit `project.yml`, never the generated project.

## Commands

```sh
just format
just format-check
just build
just build-mac
just build-ios
just test
just test-mac
just test-ios
```

Optional test filters are a test class or `ClassName/testMethod`:

```sh
just test-mac ProjectSetupTests
```

## Test output

Capture significant test runs:

```sh
mkdir -p .agent-tmp
just test 2>&1 | tee .agent-tmp/test-output.txt
```

## Build-generated string catalog updates

Xcode can rewrite `App/Localizable.xcstrings` while building or testing as it discovers
localizable strings in source code. After the final build or test:

1. Inspect `git diff -- App/Localizable.xcstrings`.
2. Include legitimate extracted entries, metadata changes and canonical reordering in the task
   commit, even when the catalog was not edited by hand.
3. If an extracted string should not be localized, fix the source declaration intentionally and
   rebuild instead of discarding or leaving the catalog rewrite uncommitted.

## Before committing

1. Run `just format`.
2. Run `just format-check`.
3. Run the relevant builds and tests.
4. Inspect and resolve any build-generated string catalog changes.
5. Fix all compiler warnings; warnings are errors in project settings.
6. Run the required reviewer cycle from `AI_ASSISTANT_GUIDE.md`.

There is no SwiftLint baseline. Do not create one or weaken thresholds to make a change pass.

## Landing changes

Push completed, committed work directly to `main` by default. Create a pull request or use the
merge queue only when the user explicitly requests that workflow. Local working branches are
fine; they do not require a pull request.

After completing the checks and reviewer gate above:

1. Fetch `origin/main` and integrate any newer commits. Resolve conflicts and rerun affected
   checks and reviews when integration changes the implementation.
2. Push the intended commit with `git push origin HEAD:main`. Use a normal fast-forward push;
   if the remote has advanced, fetch and integrate again. Never force-push `main`.
3. Verify that remote `main` contains the intended commit and monitor its CI. Fix failures before
   reporting the landing as complete.

Every push to `main` also triggers the automatic RC release workflow described in
`RELEASE_GUIDE.md`. Report any release failure separately from the source landing. Final release
tagging continues to follow the release guide's authorization and verification gates.
